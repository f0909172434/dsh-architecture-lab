# 首輪小試驗分析：隔離與驗收必須先修正

分析日期：2026-09-23。範圍為 Harness 0.1.5-rc.2、Engram 0.7.12、DeepSeek Flash／high 的 `debug-amount-A-1` 與 `debug-amount-B-1`。分析只讀取原始軌跡並執行離線探針，新增模型呼叫為零；沒有修改原始試驗、會話或預算帳本。

**結論：目前沒有證據顯示 DSH 陷入無限迴圈。真正已確認的阻礙是跨試驗答案外洩、驗收程序可被略過，以及把配額用完的試驗排除出統計的設計。** B 已受到污染；A 雖未在軌跡中觀察到跨試驗讀取，環境仍沒有強制的讀取隔離。兩筆先保留為整合診斷資料，不能據此比較記憶架構效果。

## 1. 實際發生的事情

| 觀察 | A：原生 | B：原生＋Engram |
|---|---|---|
| 有回覆的模型請求 | 12 | 12 |
| 每次回覆的結束原因 | 全部為 `tool-calls` | 全部為 `tool-calls` |
| 輸出截斷／重試事件 | 0／0 | 0／0 |
| 最大單次輸出 token | 1,955，低於 4,096 上限 | 1,735，低於 4,096 上限 |
| 自建測試通過 | 第 8 輪 | 第 11 輪 |

| 第 13 輪 | 實驗室拒絕發出新請求 | 實驗室拒絕發出新請求 |

A 第 9–11 輪製作修正前後的示範；前兩次示範出錯，再花一輪修正。第 12 輪仍是工具操作，DSH 正常需要下一次模型請求取得最終回覆；我們的硬上限在呼叫前拒絕了它。不能由此斷言「再多一輪就必定完成」，也不能稱為 DSH 的停止故障。模型收到的任務與初始提示未告知 12 次額度，沒有預先安排最後一輪只做收尾。

## 2. 已確認的隔離失敗

B 第 3–4 輪探查工作區外的目錄及評測設定，第 5–6 輪成功讀取 A 的修正答案、自建測試與報告。工具結果 `isError=false`，並確實含有程式、測試與報告內容：

| B 軌跡事件序號 | 輪次 | 讀取內容 | 回傳量 |
|---|---|---|---|
| 46 | 5 | A 的目錄、修正後 `index.mjs` 與歷史資料 | 2,750 bytes |
| 52 | 6 | A 的 `index.test.mjs` | 1,897 bytes |
| 53 | 6 | A 的 Markdown 評測報告 | 4,941 bytes |
| 55 | 6 | A 的 JSON 評測報告及任務 | 50,000 bytes |

目前的 `workspace-write` 主要約束寫入範圍，**不保證讀取範圍限於工作區**。不同資料夾和不同記憶資料庫不足以建立獨立試驗。B 讀取大篇報告後，下一次請求的輸入總 token 從約 18,000 升至 35,000，也推高後續預留成本；不能把這個差額全歸因於記憶檢索。

兩組還載入了原本使用者環境的 `autonomous-research-paper` skill 摘要。只設定 `DSH_HOME` 沒有關閉所有預設搜尋根目錄。下一版應關閉 default skill roots、固定允許來源，並在 OS／執行環境層阻止讀取其他試驗、驗收器、正式 DSH 與憑證資料；`read`、`glob` 等程序內工具和 `bash` 都需受到同一邊界限制。只檢查工具名稱或過濾 shell 字串不足以成立隔離。

## 3. 外部驗收不可靠：六題皆可重現

[`cli.mjs`](../src/cli.mjs) 用子程序載入外部 `verify.mjs`，再以 `exitCode === 0` 當作通過。每個 verifier 在自己的程序中直接 import Agent 可修改的 `index.mjs`。

離線探針把候選程式設為只有 `process.exit(0)`，沒有匯出任何待測函式；六個 verifier 都回傳 0，因此現行 CLI 會誤判通過。另一個探針證明，驗收載入候選程式時，可以寫入候選工作區外的暫存標記。所有探針只使用分析建立的臨時目錄，結束後已刪除。

**這是驗收設計漏洞的重現，不是聲稱 A 或 B 曾利用它。** 正確修法應讓候選程式在受限的獨立程序中執行，可信裁判在外部送測試輸入、比對輸出；提早退出、缺失回覆、逾時與額外副作用都不能被當作成功。只加一個可被候選程式偽造的「PASS」字串，或單靠檔案雜湊，不能代替這個邊界。

## 4. 結果分類與計價也需調整

目前 [`report.mjs`](../src/report.mjs) 的成功率只計入 `status=completed`，但 CLI 把請求額度耗盡標成 `unavailable`。如果把資源耗盡案例從分母移除，將偏袒頻繁耗盡額度的架構；先前「用了 12 次所以不能算任何形式的成功」的說法也太粗略。需要分開記錄：

- 試驗是否具備有效、未污染的評測條件；依賴缺失、隔離失敗應另列。
- 在固定資源額度內，候選成品是否通過可信外部測試。
- Agent 是否回覆完成，以及是否有錯誤完成宣告。
- 終止原因：正常、請求上限、時間上限、使用者取消、供應商錯誤等。

額度耗盡是已嘗試試驗的一種終止原因，不應自動消失於分母。客觀測試成功率與 Agent 正常收尾率應分開報告；若另設「兩者皆成功」指標，必須在新協定中先定義。這次不回寫舊紀錄或事後宣稱新的架構勝負。

| 成本項目 | A | B | 合計 |
|---|---:|---:|---:|
| 軌跡用量 × 記錄價目與匯率估算 | NT$0.3400 | NT$0.6317 | NT$0.9717 |
| 每請求向上取到分後 | NT$0.39 | NT$0.68 | NT$1.07 |
| 目前永久占用的保守預留 | NT$78.02 | NT$157.27 | NT$235.29 |

供應商帳單尚未核對；以上是用量估算，不是已核實扣款。現行預留對序列化內容用每 byte 兩 token 的估計，再乘六倍，且成功結算後也不釋放。對目前文字路線，已查源碼顯示 DSH 重試由 Agent 恢復流程重新請求，並非每個已攔截串流內必有六次未觀測文字呼叫；兩次軌跡也沒有重試事件。六倍常數尚無充分依據，不能據此判定一次小題真的花了上百元。

後續須以離線故障注入驗證「每次實際 dispatch 均可預留」，完整保存請求／attempt 識別、價格與匯率快照、快取用量，再針對確定結束且完整計量的請求結算；未知或可能已送達的請求仍保留最壞預留。此次**不釋放或重置**既有 NT$235.29，不增加 NT$300 上限。供應商帳單核對是事後核實成本的證據，不應替代可驗證的逐請求計量設計。

## 5. Engram 接口還有可重現的相容性問題

Engram 0.7.12 的 `currentUserRequestText()` 選取最後一個非空文字塊，沒有檢查訊息來源是否為真正使用者。此次 B 的 `<current_user_request>` 實際包住 skill 摘要，未包住原始修正任務；這是封包語意錯置。原始使用者任務仍在訊息中，不能據此直接推論錯置導致了跨試驗讀取。

B 沒有呼叫任何 `engram_*` 檢索工具，只收到一次自動記憶注入和額外工具定義。這次試驗不能被描述成「成功驗證 Engram 檢索」。修正應在上游獨立副本中依 `source.kind=user` 及對話角色選取真實請求，並對混入 skill／runtime 訊息的情況做回歸測試，保留原始版本與 patch。

## 6. 修正順序與解除暫停的條件

1. **先建立真正的讀取隔離與可信裁判。** 用上一試驗答案、外部測試、正式資料與哨兵檔做離線隔離測試；需要覆蓋程序內檔案工具、shell、符號連結及候選程式的驗收階段。若本機執行環境無法保證，該配方維持不可用，不以提示詞宣告隔離已完成。
2. **修正計量及完整封存協定。** 加入可核對的 dispatch 計數和結算；每筆固定價格／匯率，固定任務 prompt、profiles、system prompt、上游 patch 與裁判版本雜湊。現在的 schedule 未鎖定任務 prompt 等重要輸入，不能在改提示後沿用舊協定。
3. **修正分類、記憶訊息來源與收尾設計。** 保留每次最多 12 次請求；四組都事先得知額度，將最後一次分配給不再呼叫工具的完成／未完成回報。該機制不能讀取隱藏測試答案，也不能強制宣告成功。用離線假的模型串流驗證第 13 次永不 dispatch、取消及重開不重複花費。
4. **新協定重做小試驗後再比較。** 舊 A/B 保留為 pilot，禁止當作新協定重複測量的一部分。C/D 先離線確認規劃批准與收尾，通過上述測試後才在原 NT$300 帳本約束內恢復付費試驗；實機畫面驗收仍未完成。

新的付費試驗目前由 [`readiness.mjs`](../src/readiness.mjs) 擋住；CLI、實驗室指令及試驗 `llm/stream` 路徑均檢查，狀態與報告仍可讀。解除此技術暫停需有以上修正的驗證證據，不需要使用者再次授權同一筆預算。
