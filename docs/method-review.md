# Substantive method review — dev.9

This is a **single-agent source-and-evidence review**, not an independent review
or a model-performance study. It examines the intended estimand, fixtures,
isolation, accounting, lifecycle and reporting. The corrected design is suitable
for a bounded descriptive study of these six tasks, subject to a matching frozen
protocol receipt and the remaining graphical acceptance gate. No paid start is
enabled by this document. The original requested independent final review and
real-model comparison are still outstanding.

## Method

The estimand is the effect of **enabling each plugin bundle** under the same
model name, task input and allowance. Engram retrieval is available, not forced;
if the agent never uses it, that belongs to the enabled-feature outcome. Planning
and memory effects include their system instructions, token overhead, local
embedding work and auxiliary dispatches. This does not isolate an algorithm's
effect while holding all prompts equal.

The schedule contains 18 task/repetition blocks and 72 unique planned attempts.
The four Williams orders give each recipe four or five appearances in each
position. Task order rotates. This controls gross ordering imbalance but is
deterministic, not randomization. Provider load, shared prefix caching and the
provider's model alias remain possible time effects. No significance or
population-level generalization is proposed.

The primary outcome is verified external-test pass among every eligible launched
terminal first attempt. Failure, exhaustion and interruption remain in that
denominator. An unavailable judge is unknown and supplies no verified pass;
it is not a known failure for false-completion coding. Resumes are separate
records, never best-of replacements. Pair complete quartets within one protocol,
average repetitions within each represented task, then weight tasks equally.
Report incomplete coverage, unknown costs and marginal outcomes as well.

## Fixtures and contamination

Each recipe receives the same `history.md`. Each initial Engram database has
exactly one node matching that file; its hash and history hash match the seeding
receipt. The seeder blocks model calls. The six source histories were manually
read during this review: they contain general debugging advice or explicitly
obsolete 5%/local-time rules, not target patches or judge answers.

The reuse examples are useful hints seeded from a synthetic prior project, not
evidence naturally learned in earlier model sessions. Stale-history examples
announce the change explicitly; they do not test unannounced drift detection.
The finite cases cover the task contracts at selected inputs, not all JavaScript
values, all dates or every possible accented Latin character. Reference programs
and expected values remain outside agent workspaces and runtime images.

## Isolation, accounting and lifecycle

The candidate runs in the dedicated Linux VM/container without host shares,
general networking, provider credentials or the external judge's expected
values. The broker receives only a trial-scoped token. All direct and auxiliary
model dispatches use the same pinned route and count toward twelve requests.
The separate macOS judge accepts candidate values only; earlier-exit and forged
pass probes remain failures. This is a local macOS study, not a claim that an
unverified host has the same boundary.

The original NT$300 ledger is shared across live output roots and daily tasks.
Fresh state directories do not create a new allowance. Reservations precede each
dispatch; incomplete or uncertain usage stays charged. A ten-minute clock starts
at the first recorded controller start and includes staging and time between
resumes. Cleanup can finish after expiry; this is not further agent allowance.
Elapsed-time reports include setup and shutdown, while uncertain abrupt-loss
duration remains unknown. The old provider-day reconciliation preserves its
original entries and is a conservative aggregate, not an invoice.

Prices and FX must be checked and bound before execution; the existing validator
requires freshness within 24 hours. This review does not establish future prices.
Token-based amounts use the same quoted peak rates for comparison. Discounted
or off-peak invoices may be lower; the report does not assert an invoice total.

## Reporting and decision boundary

Research eligibility derives from matching preflight review, confirmed container
start, sealed judge/broker artifacts and original ledger entries. A registry flag
cannot qualify old or scripted records. Different protocols/images, duplicate
first attempts and unknown-cost subsets cannot be silently pooled. No automatic
winner is selected; negative and inconclusive results are legitimate outcomes.

The source tests, fixture receipt and actual isolated probes supporting this
review are summarized in [dev.9 validation](dev9-validation.json). An exact
protocol is accepted only by a separate hash-bound `purpose: research` receipt.
That receipt must identify this review as `single-agent`; it does not satisfy an
independent final review. A change to sources, image, snapshots or prices requires
fresh preparation and review. GUI acceptance and real-model experiments remain
necessary before claiming the requested mature product and empirical results.
